# Prepare the release branch

Follow the "Fill in the Changelog" and "Update the new release branch" sections
in [the release checklist](../../../.github/ISSUE_TEMPLATE/new-release.md), which
[RELEASE.md](../../../RELEASE.md) points to. Read that checklist and the
repository's `AGENTS.md` before proceeding. Resolve repository paths relative
to this skill directory, not the caller's working directory.

This skill stops at the release-branch PR. Tagging, drafting the GitHub
release, and image promotion are separate checklist steps; image and chart
verification is covered by the `verify-release-images` skill.

## Inputs and prerequisites

- Confirm the release version (`vMAJ.MIN.PATCH`) and the release issue URL or
  number with the user. Do not infer the target from the latest tag.
- Determine the release type:
  - **Patch** (`PATCH > 0`): the branch `release-MAJ.MIN` already exists; the
    previous tag is `vMAJ.MIN.(PATCH-1)`.
  - **Minor** (`PATCH == 0`): the branch `release-MAJ.MIN` must already be
    created from `main` and onboarded to Prow (earlier checklist steps); the
    previous tag is the latest release of the prior minor.
- `gh` authenticated to GitHub for PR author lookups and, when requested,
  opening the PR.
- The upstream remote fetched, including tags (`git fetch upstream --tags`).

Make changes only on a focused branch created from the up-to-date upstream
release branch. Do not push, open PRs, or create tags unless the user asks.
Never modify CI/CD workflows or release automation. Disclose AI assistance in
the PR under `#### Special notes for your reviewer:`. Do not add AI commit
trailers, `@mentions`, or issue-closing text to commit messages.

## 1. Set up the working branch

```bash
set -euo pipefail
VERSION='<vMAJ.MIN.PATCH>'
[[ "$VERSION" =~ ^v([0-9]+)\.([0-9]+)\.([0-9]+)$ ]] || {
  printf 'Expected a release version such as v0.13.1\n' >&2
  exit 1
}
MAJ="${BASH_REMATCH[1]}"; MIN="${BASH_REMATCH[2]}"; PATCH="${BASH_REMATCH[3]}"
RELEASE_BRANCH="release-${MAJ}.${MIN}"
PREV_TAG='<previous release tag>'   # confirm; see Inputs above
git fetch upstream --tags
git switch -c "prepare-${RELEASE_BRANCH}-${VERSION}" "upstream/${RELEASE_BRANCH}"
git merge-base --is-ancestor "$PREV_TAG" HEAD  # patch releases: must succeed
```

Stop if the working tree is dirty, the release branch is missing, or (for a
patch) the previous tag is not an ancestor of the release branch.

## 2. Update `BRANCH_NAME` (minor releases only)

Set `BRANCH_NAME = release-MAJ.MIN` in the `Makefile`. Skip this for patch
releases; confirm it already has the right value.

```bash
grep -n '^BRANCH_NAME' Makefile
```

## 3. Bump the version references

```bash
make prepare-release-branch VERSION="$VERSION" IMAGE_REGISTRY=registry.k8s.io/jobset
```

**Pass `IMAGE_REGISTRY=registry.k8s.io/jobset`.** The Makefile defaults
`IMAGE_REGISTRY` to the staging registry, so running the target without it
rewrites `config/components/manager/kustomization.yaml` to
`us-central1-docker.pkg.dev/k8s-staging-images/jobset/jobset`. Release branches
must point at the production registry (see #1362).

Review the diff. Expect changes only to:

- `README.md`: release manifest download URL
- `site/hugo.toml`: docs `version`
- `charts/jobset/Chart.yaml`: `version` and `appVersion` (no `v` prefix)
- `charts/jobset/README.md`: regenerated by `helm-docs`
- `config/components/manager/kustomization.yaml`: `newName:
  registry.k8s.io/jobset/jobset` and `newTag: $VERSION`
- `Makefile`: `BRANCH_NAME` (minor releases only)

```bash
git diff --stat
grep -n 'newName\|newTag' config/components/manager/kustomization.yaml
```

The `sed` in the Chart.yaml step replaces every `X.Y.Z` string in that file.
Check that it did not touch anything other than `version` and `appVersion`.

## 4. Write the CHANGELOG entry

Collect every commit in the release:

```bash
git log --format='%h %an %s' "${PREV_TAG}..HEAD"
```

For each commit:

- Read the full message (`git log -1 --format=%B <sha>`) and `git show --stat`
  to understand the user-facing effect.
- For automated cherry-picks (author `k8s-infra-cherrypick-robot`, subject or
  body "automated cherry-pick of #N"), find the original PR and its author:
  ```bash
  gh pr view <cherry-pick PR> --repo kubernetes-sigs/jobset --json body -q .body
  gh pr view <original PR> --repo kubernetes-sigs/jobset --json author -q .author.login
  ```
  Credit the original author, and list both PR numbers (`#orig, #cherry-pick`).
- Drop commits already contained in `PREV_TAG` (check with
  `git merge-base --is-ancestor <sha> "$PREV_TAG"`), the previous release-prep
  commit, and pure dependency bumps unless they fix a user-visible issue or CVE.

Group entries under the headings used in the existing
`CHANGELOG/CHANGELOG-MAJ.MIN.md`, omitting empty ones:

- `**New Features**`
- `**Bug Fixes**`
- `**Helm/Deployment**`
- `**Documentation**`
- `**Build/CI Improvements**`

Each entry is one imperative sentence describing the user-visible effect,
followed by `(#PR, @author)`. Match the two-space bullet indentation of
existing entries. Call out validation tightening, behavior changes, or anything
requiring user action on upgrade.

Prepend the section to the file, newest release first. For a new minor,
create `CHANGELOG/CHANGELOG-MAJ.MIN.md`.

```markdown
## vMAJ.MIN.PATCH

**Bug Fixes**

  - <Imperative description of the fix> (#<orig>, #<cherry-pick>, @<author>)

**Helm/Deployment**

  - <...> (#<PR>, @<author>)
```

Also paste the same text into the "Changelog" section of the release issue
(or give it to the user to paste); it is reused for the tag annotation and the
GitHub release description.

## 5. Verify

```bash
make verify
make helm-unittest
```

Report failures with their output; do not bypass linters or tests. If
`make verify` regenerates files, review them. Only the files listed in step 3
and the CHANGELOG should change.

## 6. Commit and prepare the PR

Commit with a short imperative subject, for example:

```text
Prepare release vMAJ.MIN.PATCH

Bump version references for vMAJ.MIN.PATCH and add the changelog
entry for changes since PREV_TAG.
```

When the user asks, push the branch to their fork and open a PR against
`RELEASE_BRANCH` (not `main`) using `.github/PULL_REQUEST_TEMPLATE.md`:

- Title: `[release-MAJ.MIN] Prepare release vMAJ.MIN.PATCH`
- Body: link the release issue, include the changelog, and disclose AI
  assistance under `#### Special notes for your reviewer:`.

```bash
gh pr create --repo kubernetes-sigs/jobset --base "$RELEASE_BRANCH" \
  --title "[${RELEASE_BRANCH}] Prepare release ${VERSION}" --body-file <body.md>
```

Record the PR URL in the release issue checklist (`PR: <URL>`). Example of a
previous release-prep PR: https://github.com/kubernetes-sigs/jobset/pull/1355.
